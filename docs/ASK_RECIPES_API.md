# `/ask-recipes` API — implementation notes

Spec: "Ask Recipes API" (Oct 7, 2026). Code: `ask_recipes.py` (Flask blueprint), registered at
the bottom of `app.py`, which injects the nutrition step (`_customize_recompute_nutrition`, the
same one `/customize-recipe` uses) and the image generator (`_ask_recipes_generate_image`).

**Auth & limits — same as `/customize-recipe`** (shared code in `customize_recipe.py`):
`Authorization: Bearer <Firebase ID token>` verified with the Admin SDK against `meal-plan-chef`;
same error shape; same duplicate-retry handling per uid + `X-Request-Id`; premium =
`is_premium_user == true` only. `X-Client`: `ios-app` | `android-app`.
Counter: `meal_plan_chef_users/{uid}/usage/ask_recipes_{yyyy-mm-dd}` (UTC), free 3 / premium 30,
counted only when `status = results`.

`suggestionId` (required in `suggestion` mode) accepts any id of letters, numbers, `_` or `-`
(max 50), so new cards from `app_configs/ask_recipes` work without a server change.

Endpoints:
- `POST /ask-recipes` — 1–5 complete recipes + 2–4 follow-up chips.
- `GET /ask-recipes/image/{recipeId}` — poll a pending image → `{recipeId, imageStatus, imageUrl}`
  (owner only; 404 otherwise).
- `GET /ask-recipes/suggestions` — starter cards. Reads `app_configs/ask_recipes.suggestions`
  in Firestore if present (so cards change without an app release), else a built-in list.

Processing: authenticate → validate → limit → build messages (history merged, leading assistant
dropped; final user turn = prompt + preferences + titles of shown/excluded recipes looked up in
the cache) → Claude (structured outputs) → nutrition per recipe **in parallel** → ids (`r_…`),
cache write, background images → count + log.

Server-side (not generated by Claude, to save output tokens): `id`, `totalMinutes`, ingredient
`display`, step `order`, `imageUrl/imageStatus`, `conversationId` (`c_…` when null).
Safety net: a recipe whose ingredients mention an allergy term is dropped.

Cache: `ask_recipes_cache/{id}` = `{uid, conversationId, recipe, imageUrl, imageStatus,
createdAt, expireAt}`. **Enable a Firestore TTL policy on `expireAt`** for this collection
(Console → Firestore → TTL) so documents expire after 30 days. Only the backend reads/writes it,
so no security-rule change is needed (clients are denied by default).

Images: `imageStatus: "pending"` + `imageUrl: null` in the response; `ASK_RECIPES_IMAGE_MODEL`
(default `gpt-image-1-mini`, low quality, 1024×1024) runs in the background; the PNG is resized to
768 px and re-encoded as WebP (`ASK_RECIPES_IMAGE_MAX_PX`, `ASK_RECIPES_IMAGE_FORMAT`=webp|jpeg;
falls back to the original PNG if that fails, needs `pillow`) and uploaded to the **MealMap (meal-plan-chef) Storage bucket** at
`ask-recipes-img/{id}.webp` (`upload_ask_recipe_image_bytes` in `firebase_utils.py`). The object is
permanent — not removed by the 30-day cache TTL — and the returned
`https://firebasestorage.googleapis.com/...` URL is written to the cache. If generation fails the
status becomes `ready` with `imageUrl: null` (show a placeholder). `ASK_RECIPES_IMAGES=0` turns
images off.

Saving: the app saves the Storage URL (from polling) on the saved recipe. If the user saves
before the image is ready, the server **backfills** it when the image finishes: it looks in
`meal_plan_chef_users/{uid}/recipes` for a doc whose id is the `r_…` recipe id, or that has
`askRecipeId == r_…`, and sets `imageUrl` (only if empty). So the app should save
with doc id = recipe id, or store `askRecipeId`. Field/subcollection names are configurable
(`ASK_RECIPES_SAVED_IMAGE_FIELD`, `ASK_RECIPES_SAVED_SUBCOLLECTION`).

Performance / cost:
- Model: `ASK_RECIPES_CLAUDE_MODEL`, default **Haiku 4.5** (`claude-haiku-4-5-20251001`); set
  `claude-sonnet-5-5` for the spec's original model (slower, ~2x cost).
- Output budget scales with `count`: `max_tokens = 600 + 1400 × count` (capped at 8000).
- **Answer cache** (`ask_recipes_results_cache/{hash}`, 24 h, `ASK_RECIPES_RESULTS_CACHE_HOURS`):
  first-turn requests with no history/exclusions (the "Try saying…" cards, fresh chats) with the
  same prompt + count + preferences + model reuse the stored recipes — no Claude or nutrition call,
  new `r_` ids per user, still counted as a use. Follow-ups never use it. Enable a TTL policy on
  `expireAt` for this collection too.
- **Image library** (`ask_recipes_image_library/{dish-slug}`): every generated image is recorded by
  dish name; a later recipe with the same name gets it instantly (`imageStatus: "ready"`), and the
  same dish is never generated twice at once on a worker. Pending images also resolve from the
  library when polled, and give up (`ready` + `null`) after 180 s.
- Nutrition runs for all recipes in parallel; server-derived fields aren't generated by Claude.

Model: `ASK_RECIPES_CLAUDE_MODEL` (default `claude-sonnet-5-5` per spec). Each request logs one
`[ask-recipes] {...}` line with uid, requestId, model, tokens, latency and per-step timings.

Tests: `pytest tests/test_ask_recipes.py`.
